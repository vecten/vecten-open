# Vecten Open glossary

These terms describe the files and components used to build and operate a Vecten project.

**MCP (Model Context Protocol)**: the protocol through which an agent discovers tools and calls a server; Vecten's server exposes warehouse queries and semantic definitions.

**Component**: one of the two halves of a project, `platform` or `mcp`, chosen at `vecten init` and listed in `vecten.toml`.

**Platform**: the component that loads source data with dlt, schedules work with Airflow and builds warehouse models with dbt.

**dlt**: the Python data-loading library used by Vecten connectors to extract and load records.

**dbt**: the SQL modelling tool that builds and tests tables or views in the warehouse.

**DAG**: an Airflow workflow describing tasks and their dependencies.

**Ossie / `osi/`**: Apache Ossie's semantic-model format and the project directory holding dataset and metric documents in that format.

**Dataset**: a named, described relation available to the semantic model; generated datasets correspond to dbt marts.

**Mart**: a model in the `marts` warehouse schema, shaped for a business question or reporting use.

**Convention / `vecten_convention`**: Vecten's versioned naming, description and key rules, plus the dbt package that tests them.

**Scaffold**: the initial project files generated by `vecten init`; the pristine baseline records their generated contents so `vecten update` can preserve edits.

**Profile**: the deployment layout: `standard` separates component hosts and state/warehouse databases; `minimal` shares hosts and databases where supported.

**Skill**: a set of instructions for an agent (`SKILL.md`) for one job; five ship with the CLI (`guide`, `connector`, `model`, `semantic`, `operate`), vendored into every project under `skills/` and published as a Claude Code plugin.

**Extension**: a Python package listed in `vecten.toml` that adds connectors, models, DAGs, semantic documents, skills or MCP hooks through entry points; see [extensions](extensions.md).

**Manifest**: an extension's `vecten.manifest` entry point, naming the secrets it reads and the schema of its settings; `vecten lock` records it in `extensions.lock.json`; see [secrets and settings](extensions.md#secrets-and-settings).

**Setting**: a value an extension or the project reads at run time, kept in `[settings.<extension>]` or `[settings.project]` of `vecten.toml`, with per-environment overrides under `env.<env>`; read with `vecten_shared.context`.

**Bundle**: the archive of a project's DAGs, connectors, dbt project, `osi/`, `evals/` and in-repo `extensions/` at one commit that a ship delivers to the hosts.

**In-repo extension**: an extension package kept in the project under `extensions/<name>/` and registered with `vecten extension add ./extensions/<name>`; the hosts build it from the bundle, so it is never published to or fetched from an index, while its third-party dependencies and build backend still come from one; see [extensions in the project](extensions.md#extensions-in-the-project).

**Service**: a long-running process that an extension declares in its `vecten.services` entry point and the project binds in `[services.<extension>.<service>]` of `vecten.toml`, such as a chat bot or a portal; it runs in its own container on a deployed host and on the laptop, on a hostname of its own when it has routes; see [extension services](services.md). Not the same as a service principal (`vecten service add`), which is an MCP identity for a program.

**Binding**: a service's table in `vecten.toml`, where the project chooses its hostname, the host that runs it, its limits and each route's access; `vecten extension add` writes it from the extension's suggestions, and a service or route without one does not run; see [binding a service](extensions.md#services).

**Route**: a path a service serves on its hostname, declared by the extension and bound by the project as `public` (anyone) or `login` (people signed in to the MCP who belong to one of the route's groups), optionally narrowed to listed networks by `allow`; see [access](services.md#access-public-login-and-allow).

**Gate**: the MCP's sign-in in front of `login` routes: NGINX asks the MCP server on every request whether the person may use the route, and passes the service who they are in `X-Vecten-*` headers; see [the gate](services.md#the-gate-signing-in-for-login-routes).
**Analytics app**: a dashboard an extension declares in the `vecten.apps` group and a project binds to MCP groups in `[apps.<extension>.<app>]` of `vecten.toml`; a `container` app runs as a service on its own hostname, and the MCP decides who may open it and what data it reads; see [analytics apps](analytics-apps.md).

**App principal**: the service principal `svc_app_<app>` through which an analytics app reads data from the MCP; `vecten app connect` creates or rotates it, marks it as the app's and puts it in the app's bound groups; it queries with the roles of the groups the app admits, and the MCP holds it to the app's declared datasets.

**Ship**: deliver a project's code and semantic files to existing hosts, without changing infrastructure through Terraform.

**Provisioner**: the privileged warehouse identity that creates and manages the roles used by MCP principals.

**Principal**: a person or service identity authenticated by the MCP server.

**Admin flag**: the mark on a principal that lets a person use the admin API, the admin panel and the admin tools; seeded for the addresses under `[mcp] admins`, never a warehouse privilege.

**Request chain**: the audit link between a `query_metrics` refusal and the `sql-exec` call the agent made next in the same session; see [MCP audit records](mcp-audit.md).

**Home dataset**: the one dataset a metric reads, found from its column qualifiers, an override or the dataset whose fields cover its columns; see [the semantic model guide](semantic-model.md#metrics-are-hand-written).

**Additivity**: whether a metric's result rows may be summed again: `additive`, `non_additive` or `semi_additive` (summable except across time, like a balance); see [the semantic model guide](semantic-model.md#additivity).

**Built commit**: the project commit the dbt DAG last built into the warehouse; the MCP server swaps to a shipped model only once this reaches the model's commit.

**Eval case**: an entry in `evals/semantic.yaml` holding a metric request and what it must compile to, checked by `vecten mcp validate --evals`; see [the semantic model guide](semantic-model.md#eval-cases).

**Receipt**: a server-issued identifier and execution metadata linking one MCP tool invocation to its audit record and warehouse query history; see [MCP audit records](mcp-audit.md).

**Gap**: a tracked mismatch between a question or reported answer and the available business definitions, with evidence, occurrence counts and a resolution status; see [the feedback loop](feedback-loop.md).

**Issue**: one thing broken in a running platform, as `vecten issues` lists it: a failing Airflow task, dbt test or stale source, or an open gap, with the `kind` and `resolution` of a `next` item and redacted evidence marked untrusted; see [operations](operations.md).

**`operate` skill**: the run-time counterpart of the `guide` skill: it loops on `vecten issues`, reads evidence only through `vecten issues show`, and resolves each issue through a skill, a command or a question; see [operations](operations.md#the-operate-skill).

**Admin panel**: the server-rendered pages under `/admin` on the MCP host where people with the admin flag manage identities, grants, gaps and settings and read usage analytics; see [the admin panel guide](admin-panel.md).
