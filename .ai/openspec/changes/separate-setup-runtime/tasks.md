# Implementation and release checks

This first PR proposes the design and requirement deltas. Each implementation PR targets the current release branch, adds tests for its own behavior and records which scenarios it satisfies here. Keep the change open until both providers have evidence. Estimated effort for #9 is 7–12 engineering days, with additional calendar time for approved live checks.

- [ ] **PR 1 — agent and migration contract.** Separate initialization, host transport and runtime secret resolution in the agent. Version the bundle and persistent launcher contract, refuse a mixed or missing identity before release swap, and make boot and rollback enforce the minimum safe version. Exercise legacy outputs/bundles, interrupted runs, single-component and minimal layouts. Keep the Scaleway copy byte-identical and Python 3.9 compatible. Ship preparatory support with explicit legacy detection.
- [ ] **PR 2 — AWS.** Add operator-owned runtime roles, exact trust and host STS ceiling, a host credential refresher, SDK profile and read-only mounts. Move Airflow initialization, block metadata before any container starts and change the trusted SQL helper's network. Test bootstrap reconciliation, Terraform policies, Compose generation and real SDK renewal in Docker. Include the AWS cutover and recovery procedure.
- [ ] **PR 3 — Scaleway.** Split IAM policies, implement two-key delivery, purpose-specific verified receipts, cancellation cleanup, rotation and old-application policy reduction. Install the watcher and metadata guard on existing hosts before placing the new entry. Cover Terraform state safety, mirrored agent behavior, generated runbook and retry/rollback. This PR can follow PR 1 independently of the AWS implementation.
- [ ] **PR 4 — migration acceptance and operator docs.** Exercise generated projects upgrading from the legacy release on both clouds, run the matrix below and document recovery. Update SECURITY.md, docs/mcp-identity.md, docs/deploy-aws.md, docs/deploy-scaleway.md and the scaffold template docs/runbook.md.jinja to identify the versions and environment cutover required for the narrower trust model. Keep the limitation documented for legacy installations. Attach sanitized results to #9 and hand AWS policy inputs to #11.

## Verification matrix

Offline checks are merge criteria. Live checks are separate release work and require approval naming the sandbox and the changes on each cloud. Record the release commit, layout, actor, operation, expected and actual result, and provider denial/error code. Omit keys, secret values, password hashes and credential responses. Use known existing synthetic secrets for negative reads and a disposable target for write checks, so a missing resource or network failure cannot masquerade as an authorization denial.

| Test | AWS evidence | Scaleway evidence |
| --- | --- | --- |
| Policy and layout, offline | Decode Terraform policies and bootstrap ceilings/trust. Assert exact master ARNs, generation names, scoped role assumption, no runtime SSM/assumption/initialization, IMDSv2 and hop 1. | Assert application, project, path and exact-name conditions including secret metadata vs value access. Assert bucket grants, independent rotation and receipt validation, and absence of keys in Terraform inputs/outputs. |
| Workload and agent, offline | Run the real image SDK and Airflow log handler through session renewal, a refresher outage and recovery. Inspect rendered mounts and build settings. | Fake Instances, IAM, Secret Manager and object storage. Cover old watcher, one missing key, stale/replayed receipt, replacement VM, rotation during a failed deploy, timeout and interrupted metadata cleanup. Assert no setup key in Compose, S3 connection or error output. |
| Fresh deploy and upgrade, live | In an approved sandbox, prove SSM still reaches the host, the agent runs setup twice, and MCP and Airflow report the runtime role. Repeat through actual STS expiry/refresh in a long-lived process. | In an approved sandbox, reconcile the master, confirm both receipts, prove both entries are removed and a subsequent refresh is safe. Run setup twice and verify key rotation and forced recreation, then denial for the retired key. |
| Effective denial, live | From each enabled container network, including the DAG worker, MCP, extension, build and transient SQL helper, verify metadata is unavailable. With the actual runtime session, validate denial of each managed master, setup-only write, role escalation and other scopes. | Test metadata isolation during handoff and after Docker restart on both address families in use. With the actual runtime key, validate denial of each admin secret by ID as well as by path, writes to MCP_STATE_DB_PASSWORD and every other setup-initialized password except the runtime-rotatable MCP_IMPERSONATOR_PASSWORD, deploy secrets, state bucket and another environment's values. Verify setup succeeds with its own key. |

**Runtime operations on both clouds.** Run a DAG that reads its connector secret, writes and rereads a remote task log and publishes dbt artifacts. Through MCP read the three build records, query the warehouse, initialize signing and exercise supported impersonator rotation. Verify allowed reads and writes in the component prefix and denied bundle writes.

**Lifecycle on both clouds.** Cover fresh and legacy combined standard and minimal installations, platform-only and MCP-only, and the Snowflake or external-warehouse state-only setup path. Use parameterized CI tests across the full matrix. On each cloud exercise both a shared and a split host in the sandbox, a content ship, host reboot, interrupted cutover, health-poll rollback, host replacement, DB restore, re-ship and cleanup. Verify data and credential continuity and sibling isolation.

Use the repository's unit, Docker and Terraform tiers for the corresponding implementation changes. Recheck setup-host selection, build isolation and runtime operations against the release head when these PRs land.
